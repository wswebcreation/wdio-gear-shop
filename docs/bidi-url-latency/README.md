# BiDi `browsingContext.navigate` driver latency (issue #15481)

Permanent copies of the benchmark output from GitHub Actions run
[32113009915](https://github.com/wswebcreation/wdio-gear-shop/actions/runs/32113009915)
(Linux + macOS, 3 runs each, 15 iterations, `http://127.0.0.1:4173/index.html`).

Generated by [`scripts/debug-driver-latency.mjs`](../../scripts/debug-driver-latency.mjs) via the
[Driver latency workflow](../../.github/workflows/driver-latency.yml).

Related:

- [webdriverio/webdriverio#15481](https://github.com/webdriverio/webdriverio/issues/15481) — WDIO `browser.url()` slowness on macOS BiDi
- Upstream report target: [GoogleChromeLabs/chromium-bidi](https://github.com/GoogleChromeLabs/chromium-bidi)

## Summary (median ms)

| Platform | Run | Classic `navigateTo` | BiDi `navigate` (WDIO) | BiDi WebSocket `browsingContext.navigate` | BiDi WebSocket `getTree` |
|----------|-----|----------------------|------------------------|---------------------------------------------|--------------------------|
| Linux | 1 | 141 | 116 | 95 | 1 |
| Linux | 2 | 134 | 135 | 98 | 1 |
| Linux | 3 | 136 | 113 | 94 | 1 |
| macOS | 1 | 135 | 1311 | 1236 | 26 |
| macOS | 2 | 130 | 667 | 623 | 18 |
| macOS | 3 | 79 | 592 | 573 | 23 |

On Linux CI, classic and BiDi navigate are in the same ballpark. On macOS CI, BiDi
`browsingContext.navigate` is ~5–10× slower at the WebSocket layer while `getTree` stays cheap.

Chrome **151.0.7922.108**, headless Chrome-for-Testing via WebdriverIO.
